# Аналитическая платформа интернет-магазина

Сквозной конвейер обработки данных интернет-магазина: платформа загружает данные из
трёх связанных источников, проверяет их качество и ведёт журнал отбракованных записей,
объединяет источники в единый набор, строит многоуровневую аналитику, выявляет
аномальные заказы и формирует итоговый отчёт с экспортом в несколько форматов.

Проект приближен к реальной работе аналитика данных: сведения о заказах, товарах и
клиентах хранятся отдельно и связываются по идентификаторам, а сами данные содержат
пропуски, опечатки и ошибки, которые нужно отсеять, не потеряв остальную информацию.

Всё решение находится в блокноте **[`analytical_platform.ipynb`](analytical_platform.ipynb)**
и запускается как в Google Colab, так и локально.

## Схема данных

Платформа работает с тремя файлами. Каждый описывает свою сущность, а связи между ними
устанавливаются по идентификаторам: заказ ссылается на товар через `product_id` и на
покупателя через `customer_id`.

```
      customers.csv                orders.csv                 products.csv
   ┌─────────────────┐        ┌──────────────────┐        ┌─────────────────┐
   │ customer_id  PK │◄───────┤ customer_id   FK │        │ product_id   PK │
   │ name            │        │ product_id    FK ├───────►│ name            │
   │ city            │        │ order_id      PK │        │ category        │
   │ registration_…  │        │ order_date       │        │ unit_price      │
   │ segment         │        │ quantity         │        │ in_stock        │
   └─────────────────┘        │ status           │        └─────────────────┘
          8 строк             └──────────────────┘              10 строк
                                    28 строк
```

| Файл | Сущность | Строк | Ключ | Поля |
|------|----------|-------|------|------|
| `customers.csv` | покупатели | 8 | `customer_id` | `name`, `city`, `registration_date`, `segment` |
| `products.csv` | каталог товаров | 10 | `product_id` | `name`, `category`, `unit_price`, `in_stock` |
| `orders.csv` | заказы | 28 | `order_id` | `order_date`, `customer_id`, `product_id`, `quantity`, `status` |

Справочные значения: категории — «Книги», «Электроника», «Одежда»; города — Москва,
Санкт-Петербург, Казань, Новосибирск; сегменты — «опт», «розница»; статусы заказа —
`completed`, `cancelled`, `pending`.

**В выручке учитываются только заказы со статусом `completed`**, записи `cancelled`
и `pending` из расчётов исключаются.

## Заложенные дефекты данных

В файле заказов намеренно присутствуют пять проблемных строк. Платформа обязана
отбраковать их, не прерывая работу, и записать в журнал с указанием причины.

| Заказ | Что не так | Причина отбраковки | Как обнаруживается |
|-------|------------|--------------------|--------------------|
| 12 | `quantity = "x"` | нечисловое количество | `try / except ValueError` |
| 15 | `quantity = ""` | нечисловое количество | `try / except ValueError` |
| 17 | `product_id = "p99"` | неизвестный товар | проверка `in` по каталогу товаров |
| 19 | `customer_id = "c99"` | неизвестный покупатель | проверка `in` по базе покупателей |
| 21 | `quantity = -1` | неположительное количество | сравнение `quantity <= 0` |

Проверки выстроены по очереди, и первая же сработавшая причина отправляет строку
в брак, после чего обработка переходит к следующей записи.

## Архитектура конвейера

```

   │   Этап 1     │   │   Этап 2     │   │   Этап 3     │   │   Этап 4     │
   │  подготовка  ├──►│   загрузка   ├──►│  валидация   ├──►│ объединение  │
   │    файлов    │   │  каталогов   │   │  + журнал    │   │   по ключу   │
   └──────────────┘   └──────────────┘   └──────┬───────┘   └──────┬───────┘
                                                │                  │
                                         rejected.csv              ▼
                                                           ┌──────────────┐
                                                           │   Этап 5     │
                                                           │ нормализация │
                                                           └──────┬───────┘
                                                                  ▼
            ┌──────────────┬──────────────────┬──────────────────┐
            ▼              ▼                  ▼                  │
     ┌─────────────┐ ┌─────────────┐  ┌──────────────┐           │
     │   Этап 6    │ │   Этап 7    │  │   Этап 8     │           │
     │   чистый    │ │   NumPy:    │  │   Pandas:    │           │
     │   Python    │ │ статистика  │  │   сводные    │           │
     │             │ │ и аномалии  │  │   таблицы    │           │
     └──────┬──────┘ └──────┬──────┘  └──────┬───────┘           │
            └───────────────┴────────────────┘                   │
                            ▼                                    │
                     ┌──────────────┐                            │
                     │   Этап 9     │  report.txt                │
                     │   пайплайн   ├─► summary.json             │
```

Каждый этап оформлен отдельной функцией, а `run_pipeline()` собирает их в единую
последовательность, где результат каждого шага передаётся следующему.

## Этапы и состав функций

### Этап 1. Подготовка файлов данных

```python
save_dataset(rows, filename) -> str
prepare_files() -> tuple[str, str, str]
```

`save_dataset` записывает список строк в CSV-файл через `with`, модулем `csv`,
в кодировке `utf-8` и одним вызовом `writerows`. Функция переиспользуется на этапе 3
для записи журнала отбраковки, что избавляет от дублирования кода записи CSV.

### Этап 2. Загрузка каталогов в словари

```python
load_products(filename)  -> dict[str, dict]   # {product_id: {...}}
load_customers(filename) -> dict[str, dict]   # {customer_id: {...}}
```

Обе функции построены на общем загрузчике `_load_catalog`, которому передаётся имя
ключевого поля и список полей для приведения к `float`. Файлы читаются через
`csv.DictReader`, цена товара приводится к `float`, отсутствие файла перехватывается
через `FileNotFoundError` и не роняет программу.

Словарь с идентификатором в качестве ключа выбран осознанно: поиск товара или
покупателя становится операцией за константное время, тогда как по списку пришлось бы
каждый раз делать полный перебор.

```python
products["p2"]
# {'product_id': 'p2', 'name': 'Наушники', 'category': 'Электроника',
#  'unit_price': 2300.0, 'in_stock': 'yes'}
```

### Этап 3. Валидация заказов и журнал отбраковки

```python
validate_orders(filename, products, customers, log_file="rejected.csv")
    -> tuple[list[dict], list[tuple[str, str]]]
```

Возвращает кортеж из списка корректных заказов и списка отбракованных записей.
Причина хранится рядом с идентификатором заказа в **кортеже** — неизменяемой паре
«идентификатор и причина». Журнал параллельно пишется в `rejected.csv`.

```python
valid, rejected = validate_orders("orders.csv", products, customers)
len(valid)   # 23
rejected     # [('12', 'нечисловое количество'), ('15', 'нечисловое количество'),
             #  ('17', 'неизвестный товар'), ('19', 'неизвестный покупатель'),
             #  ('21', 'неположительное количество')]
```

### Этап 4. Объединение источников данных

```python
enrich_orders(valid_orders, products, customers) -> list[dict]
```

Ручной аналог соединения трёх таблиц по ключу — то, что в Pandas делается методом
`merge`. К каждому заказу добавляются `product`, `category`, `price`, `customer`,
`city`, `segment` и вычисленная выручка `revenue = quantity * price`.

Исходные каталоги не изменяются: заказ копируется через `dict()`, а из справочников
берутся только значения.

### Этап 5. Нормализация текстовых полей

```python
clean_text(value, rule) -> str
normalize_orders(orders) -> list[dict]
```

Правила вынесены в словарь `NORMALIZATION_RULES`, поэтому добавить новое поле — значит
дописать одну строку, а не ещё одну ветку кода:

| Поле | Правило | Зачем |
|------|---------|-------|
| `customer`, `city`, `category` | `strip` + `title` | единое написание имён, городов и категорий |
| `product` | только `strip` | `.title()` испортил бы «Python для начинающих» |
| `status`, `segment` | `strip` + `lower` | надёжное сравнение при фильтрации и группировке |

Числовые поля (`quantity`, `price`, `revenue`) не затрагиваются. Лишние пробелы
схлопываются не только по краям, но и внутри строки.

### Этап 6. Аналитика на чистом Python

```python
completed_only(orders)                    -> list[dict]
total_revenue(orders)                     -> float
revenue_by(orders, field)                 -> dict[str, float]
top_by(orders, key_field, value_field, n) -> list[tuple]
top_customers(orders, n=3)                -> list[tuple[str, float]]
top_products(orders, n=3)                 -> list[tuple[str, int]]
unique_values(orders, field)              -> set
```

Ключевая функция — обобщённая `revenue_by(orders, field)`: имя поля передаётся
параметром, поэтому одна функция считает выручку и по категориям, и по городам,
и по сегментам. По той же причине `top_customers` и `top_products` построены на общем
помощнике `top_by` и различаются только тем, какое поле группируется и какое суммируется.

### Этап 7. Статистика и поиск аномалий средствами NumPy

```python
revenue_array(orders)                -> np.ndarray
revenue_analytics(orders)            -> dict[str, float]
anomaly_threshold(orders, sigma=2)   -> float
find_anomalies(orders, sigma=2)      -> list[dict]
```

Выручка собирается в массив NumPy, по которому считаются средний чек, медиана,
стандартное отклонение и квартили. Аномально крупным считается заказ с выручкой выше
порога `среднее + 2 × стандартное отклонение`. Отбор выполняется логической
индексацией: условие, применённое к массиву, даёт булеву маску, и этой маской сразу
выбираются нужные заказы — **без явного цикла**.

### Этап 8. Многомерный анализ средствами Pandas

```python
build_dataframe(orders)      -> pd.DataFrame
category_segment_pivot(df)   -> pd.DataFrame
```

Сводная таблица «категория × сегмент» строится одним вызовом `pivot_table` с
`aggfunc="sum"` и `fill_value=0`. Дополнительно выводится распределение по категориям
через `groupby` с агрегатами `sum`, `mean`, `count`.

### Этап 9. Сборка пайплайна и отчёты

```python
build_summary(total_rows, rejected, valid, completed_orders) -> dict
format_report(summary)        -> str
export_json(summary, filename="summary.json")
export_csv(rows, filename="revenue_by_category.csv", header=("key", "revenue"))
export_report(report, filename="report.txt")
run_pipeline(verbose=True)    -> dict
```

`run_pipeline` читается как цепочка шагов: подготовка файлов → загрузка каталогов →
валидация → обогащение → нормализация → аналитика → статистика → отчёт. Сводные
показатели собираются в один словарь, который и выводится в отчёт, и экспортируется
в JSON с `ensure_ascii=False`, чтобы кириллица осталась читаемой.

Функция возвращает словарь-контекст со всеми промежуточными результатами — каталогами,
заказами, сводкой, текстом отчёта, статистикой, аномалиями и `DataFrame`, — чтобы
интерактивная консоль пользовалась готовыми данными без пересчёта.

### Этап 10. Интерактивная аналитическая консоль

```python
console(ask=input, context=None) -> None
```

Цикл `while` повторяет меню, пока не выбран выход; на неверный ввод выводится
сообщение, и работа продолжается. Пункт «выручка по разрезу» опирается на обобщённую
`revenue_by` из этапа 6: пользователь выбирает поле, а считает его та же самая функция.

```
=== АНАЛИТИЧЕСКАЯ КОНСОЛЬ ===
1 — полный отчёт
2 — выручка по разрезу
3 — топ покупателей и товаров
4 — аномальные заказы
5 — сохранить отчёты в файлы
0 — выход
```

Параметр `ask` по умолчанию равен встроенной `input`, но его можно подменить. Это
позволяет показать работу консоли в блокноте, который должен выполняться целиком без
остановки на ручном вводе: в демонстрационной ячейке сценарий ответов проходит по всем
пунктам меню, включая неверный разрез и неверный пункт. Для живой работы достаточно
раскомментировать вызов `console()` в последней ячейке этапа 10.

## Контроль корректности

В блокнот встроены две проверочные ячейки, которые выполняются вместе с остальными
и падают с ошибкой при расхождении.

**Сверка трёх подходов к аналитике** — ручной подсчёт из этапа 6 сравнивается
с результатами Pandas и NumPy:

```python
assert manual == pandas_result
assert round(df["revenue"].mean(), 2) == revenue_analytics(completed)["mean"]
assert float(df["revenue"].sum()) == total_revenue(completed)
```

**Сверка контрольных значений** — все итоговые показатели сравниваются с ожидаемыми
из условия задачи: 28 строк, 5 отбраковано, 23 корректных, 20 завершённых, выручка
86 350.00, средний чек 4 317.50, медианный 3 750.00, одна аномалия.

Дополнительно проверяется, что обработка отсутствующего файла не прерывает программу,
а каталоги после обогащения заказов остаются неизменными.

## Принятые инженерные решения

**Выбор структур данных под задачу**

| Структура | Где используется | Почему именно она |
|-----------|------------------|-------------------|
| Словарь-каталог | `products`, `customers` | мгновенный поиск по идентификатору вместо полного перебора списка |
| Кортеж | `(order_id, причина)` | неизменяемая пара, которая не должна меняться после записи в журнал |
| Множество | `unique_values`, `BREAKDOWN_CODES` | уникальные значения и быстрая проверка принадлежности при вводе |
| Список | заказы на всех этапах | упорядоченный набор, который последовательно обрабатывается |
| Словарь-сводка | `summary` | один источник данных и для текстового отчёта, и для JSON |

**Отсутствие дублирования.** Обобщённые функции заменяют почти одинаковый код:
`revenue_by(orders, field)` вместо трёх функций под категории, города и сегменты;
`top_by` как основа для `top_customers` и `top_products`; `_load_catalog` как основа
для `load_products` и `load_customers`; `save_dataset` одновременно для исходных
файлов и для журнала отбраковки.

**Устойчивость к некорректным данным.** Преобразование количества обёрнуто в
`try / except`, принадлежность каталогам проверяется через `in`, отсутствие файла
перехватывается через `FileNotFoundError`. Ни один из пяти дефектов данных не прерывает
работу: все они попадают в журнал с указанием причины.

**Константы вместо «магических» значений.** Имена файлов, формулировки причин
отбраковки, статус завершённого заказа, число сигм для порога аномалии и размер топа
вынесены в именованные константы в начале соответствующих этапов.

**Тестируемость интерактивной части.** Параметр `ask` у `console()` позволяет
подменить источник ввода, благодаря чему интерактивный сценарий воспроизводится
в автоматическом прогоне блокнота.
